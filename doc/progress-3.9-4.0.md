## 0. 一页结论

1. **全量做到 v4.0 约需 289.0 人日 / 58.1 个自然周（单人，约 13 个月）**，含 33.0 人日阶段缓冲。规模主要来自 A-2 迁移、U 的 UI/动效重构与 B/C 的引擎研究，而不是业务代码量。
2. **第一个可发布版本（v3.9.0）只需 41.5 人日 / 约 8.3 周**；报告把排序筛选、倍速、格式状态、M3U、体检整合、内存索引都归为「相对廉价」项，建议先批这一段。
3. **新增阶段 U（UI/动效系统化重构，9 项需求）73.0 人日 / 约 14.4 周，插入 A-1 之后、A-2 之前**：交付 v3.10.0。覆盖液态琉璃胶囊/迷你播放器、首页听歌统计卡、多选菜单统一、歌词设置页、定时关闭、Elastic 进度条、首字母筛选、下拉扫描、转场强化，以及 Skeleton/动效/无障碍补齐。放在 A-2 前是因为这 9 项基本不依赖存储迁移，先交付用户可感知的部分；A-2 只需在扫描改造时回归 U-08。
4. **U 的起点比工具阶段差**：核心列表页（Download / Leaderboard / SongList / Mine / Setting / Player Stage / ProgressBar）实测 0 处 `Animated`，全仓无 Skeleton 组件、accessibilityLabel 仅 13 处；项目也没有 Reanimated / Gesture Handler，动效全部走 RN `Animated`。所以 U-00 先出 D8（是否引入动画依赖、低端机降级、reduce-motion），再动手实现。
5. **新增阶段 T（音乐工具强化，对标 Lyrico）30.0 人日 / 约 6 周，插入 A-2 之后、B 之前**：交付 v3.12.0「曲库 + 工具」版本。工具要改用户曲库文件，放在迁移与身份模型稳定之后，用 T-01 队列 + 写前快照兜住数据风险。
6. **工具不是从零做**：EmoMusic 已有元数据弹窗、歌曲信息页、批量刮削/补封面/补歌词/批量重命名、9 项体检和全局任务锁（代码证据见 §2.4）。阶段 T 主要补「完整字段与写入策略、批量编辑、歌词格式能力、任务队列与历史、外部编辑入口」，难度约 6/10，低于 A-2/B/C。
7. **开工第一步仍是 S0-00**：核验显示工作区 146 项变更（70 M + 68 D + 8 未跟踪；编制本表后 148），其中 4 个未跟踪文件是被 16 处已跟踪代码 import 的源码模块——现状不可回退、clean clone 也编译不过；且全仓没有任何 v3.x tag（最新 v1.9.2）。S0-00 从 1.0 上调到 1.5 人日。这批变更里有 7,428 行删除（定时退出/桌面歌词/sync/评论/备份页），其中定时关闭在 HEAD 仍有实现，U-05 可对照恢复。
8. **排期单点风险**：A-2（38 人日、不可逆迁移）、B-03（FFmpeg 本地编译 12 人日）、T 的写标签链路（文件重写可能损坏）、U 的动效性能与依赖（R9/R10）各配 5 / 7 / 3.5 / 5 人日缓冲并设门禁；不通过就降级或换路线，不允许为赶版本把未验证项写成「已支持」。
9. **B/C 只批 PoC 预算、D 不进发布计划**：U（用户可感知的 UI）与 T（曲库工具）先于引擎 PoC（B）交付，因为 FFmpeg/DSD 是研究性投入，且 C/D 的听感验收无法靠 CI 断言。

|---|---|

| 节奏 | 5 工作日/周；1 人日 = 6 有效小时，不含会议、支持与真机排队 |
| 起点 | 2026-11-09（报告生成后的首个周一） |
| 日历 | 已扣除周末，**未扣除法定节假日**（假期与设备不可用由各阶段缓冲抵扣） |
| 估算 | P50 中位数，粒度 ≥0.5 人日；依据报告 §4 难度拆分、§6 任务卡、现有代码规模（src 82,055 行）与 Lyrico 能力清单 |
| 偏差校准 | 每阶段门禁按「已完成人日 / 计划人日」重估剩余；偏差 >25% 必须重排并记版本号 |
| 状态定义 | PASS / PARTIAL / FAIL / NOT RUN（说明书附录 A）；**NOT RUN ≠ 通过** |
| 进度算法 | 按人日加权（Σ人日×完成度 / Σ人日），不按任务条数 |
| 依赖 | 同阶段内默认串行（单人）；跨阶段门禁未过不得启动下一阶段 |
| 半日任务 | 0.5 人日任务会与前/后任务同日交接（如上午收尾、下午开工），表中出现同日重叠属正常 |
| 设备 | 当前 `adb devices` 为空、无真机；所有真机验收任务依赖先解决设备/云真机，否则只能标 NOT RUN |
| 不做 | 在线音源接口可用性、iOS、上架商店合规改造（合规项列在 §7 可选批次 O-01～O-04） |

> 人日为**计划值**，不是承诺值。报告 §8 明确 6 项运行时事实未验证，任何一项被证伪都可能导致重估；这也是各阶段设缓冲的原因。

### 2.4 音乐工具能力对标（Lyrico → EmoMusic）

Lyrico 是**标签编辑器**（不是播放器）：单曲编辑、批量编辑、歌词/封面/ReplayGain 工具、插件源、任务历史。下表按「实际代码」对照，避免把已有能力当缺口：

| 能力 | Lyrico 参考 | EmoMusic 现状（代码证据） | 差距 | 对应任务 |
|---|---|---|---|---|
| 单曲标签编辑 | 完整编辑页：标题/艺术家/专辑/专辑艺术家/年份/流派/音轨/碟号/作曲/作词/注释 + 自定义标签 + 字段显隐排序 | MetadataEditModal 仅 歌名/歌手/专辑 + 封面/歌词/文件名；SongInfoPage 可编辑 6 字段（年份/音轨/碟/流派仅 FLAC 可写） | 字段不全、入口分散、非 FLAC 扩展字段受限 | T-02 |
| 批量标签编辑 | 多选后 keep/清空/写入三态 + 从已选取值 + 预览 + 并发 + 封面/自定义标签 | 无；只有整批刮削（tagScrape 自动写 歌名/歌手/专辑） | 缺 | T-03 |
| 标签匹配 | 插件式多源、候选详情、应用/仅歌词、写入规则 补充/覆盖/禁用、并发限流 | scrape.ts 固定 kw/tx/wy 三源，自动取最高分，无候选/无写入规则/串行 | 有基础但不可控 | T+-03 |
| 歌词工具 | LRC↔TTML、逐字时间轴、偏移 ±100ms、简繁转换、歌词整理、批量导入导出、批量匹配歌词 | 逐字仅显示；无 TTML/偏移/简繁/整理；lyricFix 仅写同名 .lrc | 缺编辑与格式能力 | T-04 |
| 封面与艺术家海报 | 内嵌/外置海报文件夹、裁剪、批量匹配封面、导出、MP4/M4A 限制标注 | coverFix 补封面（内嵌→网络→仅曲库降级）；无裁剪/海报/导出 | 缺 | T+-01 |
